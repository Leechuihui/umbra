### 第一章 · 架构认知（1:30–4:00）

**画面**：切到 `01-architecture.svg`

**旁白**：

> 先讲清楚 UMBRA 的三层架构，这是理解后面所有操作的基础。
>
> **第一层：团队服务器**
> Python 写的，默认监听 9000 端口。它是整个系统的中枢——接收植入体回连、存储数据、给客户端提供 API。
>
> **第二层：操作员客户端**
> Electron + React 写的桌面程序。通过 HTTP API 跟服务端通信。
>
> **第三层：植入体**
> 运行在目标机器上的程序。主动回连服务端，接收指令。
>
> **关键设计：客户端和植入体永不直接通信。**
>
> 为什么这么设计？三个原因：
> 1. **客户端可以随时关机**，植入体依然在线，数据不会丢
> 2. **植入体被分析也拿不到操作员信息**，因为它只知道服务端地址
> 3. **多个操作员可以同时管理同一批植入体**，服务端做协调

**操作演示**：
1. 点击右上角 🌐 图标 → 切换中文 → 再切回英文
2. 点击 🎨 图标 → 依次切换 4 套主题

**旁白**：

> 顺便展示两个原创功能：
> - **双语界面**：点地球图标，中英文实时切换，会记住你的选择
> - **主题系统**：暗影青、余烬橙、深渊蓝、单色，四套配色

### 第二章 · 环境规划（4:00–8:00）★最关键

**画面**：切到 `02-network-topology.svg`

**旁白**：

> 这一章是**整期视频最重要的部分**，90% 的人卡在这里。
>
> 我的实验环境：
> - **Kali**：攻击机，IP `10.0.2.15`，**NAT 网络**
> - **webserver**：靶机，IP `192.168.1.46`，**桥接网络**
> - **宿主机**：Windows，IP `192.168.1.38`

**画面**：在 Kali 终端执行

```bash
ip addr show eth0 | grep inet
# inet 10.0.2.15/24
```

**旁白**（语速放慢）：

> 现在讲**最关键的坑**。
>
> Kali 在 NAT 网络里，IP 是 `10.0.2.15`。这是 VirtualBox 内部的私有地址，**外部世界根本路由不到**。
>
> 意味着什么？
> - Kali **能主动访问**目标机 ✅
> - 目标机**无法反向连回** Kali ❌
>
> 而植入体是**主动回连**的。如果 C2 地址填 Kali 的 IP，回连 100% 失败。
>
> **这就是为什么很多人照着教程做，会话永远不上线。**

**画面**：在 webserver 上验证

```bash
ping 10.0.2.15
# 100% packet loss —— 连不通
```

**旁白**：

> 实测确认，目标机 ping 不通 Kali。

**画面**：切回宿主机，执行端口转发

```powershell
VBoxManage controlvm kali natpf1 "umbra-http,tcp,,8080,,8080"
VBoxManage controlvm kali natpf1 "umbra-api,tcp,,9000,,9000"
```

**旁白**：

> 两条命令，含义是：
> - 宿主机 `8080` → 转发到 Kali `8080`（植入体回连用）
> - 宿主机 `9000` → 转发到 Kali `9000`（客户端连服务端用）
>
> 所以后面植入体的 C2 地址要填 **`192.168.1.38:8080`**，**不是 Kali 的 IP**。
>
> 这一点必须记牢，讲错就全盘失败。

**画面**：验证转发链路

```powershell
VBoxManage showvminfo kali --machinereadable | findstr Forwarding
# Forwarding(0)="umbra-http,tcp,,8080,,8080"
# Forwarding(1)="umbra-api,tcp,,9000,,9000"
```

```bash
# Kali 里监听
nc -l -p 8080
```

```powershell
# 宿主机发数据
Test-NetConnection -ComputerName 192.168.1.38 -Port 8080
# TcpTestSucceeded : True
```

**旁白**：

> 实测验证：从宿主机向 `192.168.1.38:8080` 发数据，Kali 成功收到。
>
> 链路通了，可以继续。

**知识点卡片**：
| 概念 | 说明 |
|---|---|
| NAT 网络 | 私有网段，外部无法直接访问 |
| 桥接网络 | 像真实机器接入局域网 |
| 端口转发 | 宿主机端口映射到虚拟机 |
| 反向连接 | 植入体主动连出，绕过入站防火墙 |

### 第三章 · 部署 UMBRA（8:00–11:00）

**画面**：终端

```bash
git clone https://github.com/Leechuihui/umbra.git
cd umbra
sudo bash install.sh all
```

**旁白**：

> 一条命令完成部署。脚本自动做五件事：
> 1. 安装系统依赖（编译器、Python、Node.js）
> 2. 创建 Python 虚拟环境，装 28 个依赖包
> 3. 编译 SGN 编码器（Rust）
> 4. 构建 Electron 客户端
> 5. 创建桌面快捷方式和图标

**画面**：安装过程加速播放（4×–8×）

**旁白**（讲工程细节）：

> 安装过程中，我讲几个**工程细节**，你能看出成熟项目和玩具项目的区别。
>
> **第一，t64 包名迁移**
> Ubuntu 24.04 之后，很多系统库因为 64 位时间戳迁移改了名字。比如 `libgtk-3-0` 变成了 `libgtk-3-0t64`。
> 脚本会自动检测，新名字不行就用旧名字，不会因为一个包名变化就中断安装。
>
> **第二，tmpfs 空间陷阱**
> 很多系统上 `/tmp` 是内存盘，只有 1–2G。打包 AppImage 需要 2G 以上，会报 `ENOSPC`。
> 脚本会把临时目录重定向到磁盘上，避开这个坑。
>
> **第三，逐包安装**
> 不是一次性 `apt install 一堆包`，而是逐个装。某个包不可用只警告，不会让整个安装失败。
>
> **这就是真实环境下的健壮性设计。**

**画面**：验证安装

```bash
ls -lh client/gui/dist/umbra.AppImage     # 约 149M
ls -d server/venv                          # Python 环境
./umbra.py version                         # 版本号
```

### 第四章 · 启动服务端与客户端（11:00–15:00）

#### 4.1 创建操作员密钥

```bash
cd /opt/umbra
./umbra.py server key add admin
```

**输出**（重点展示）：
```
admin:CjzeeStPQ9wfCnyH5iwHKzK:BtdxBz5pYq4fcOpF...
Operator created successfully: admin
Saved: /opt/umbra/admin.key
```

**旁白**：

> 这是**三段式密钥**：`用户名:密码:密钥`。
>
> 为什么三段？这是**双因素认证**设计：
> - 第一段用户名：标识身份
> - 第二段密码：验证"你知道什么"
> - 第三段密钥：验证"你持有什么"
>
> 服务端存的是密码的 bcrypt 哈希，密钥明文比对。即使数据库泄露，攻击者也拿不到明文密码。
>
> **整行都要复制保存**，只显示这一次。

#### 4.2 启动服务端

```bash
./umbra.py server start
```

**输出**：
```
INFO:     Uvicorn running on http://0.0.0.0:9000
```

**旁白**：

> 服务端起来了，监听所有网卡的 9000 端口。
>
> **这个终端不能关。** 建议 `Ctrl+Shift+T` 开新终端做后续操作。

**验证**：
```bash
ss -ltn | grep 9000
# LISTEN 0 2048 0.0.0.0:9000 0.0.0.0:*
```

#### 4.3 启动客户端

```bash
export DISPLAY=:0
/opt/umbra/client/gui/dist/umbra.AppImage --appimage-extract-and-run --no-sandbox
```

**旁白**：

> 两个参数要解释：
>
> **`--appimage-extract-and-run`**
> AppImage 格式需要 libfuse2 才能挂载运行，但 Kali 只提供 libfuse3。所以要先解压再运行。
> UMBRA 会自动检测，没有 libfuse2 就自动加这个参数。
>
> **`--no-sandbox`**
> 以 root 运行时 Chromium 沙箱会冲突，需要关闭。
>
> 也可以直接用桌面快捷方式「UMBRA」，安装脚本已经创建好了，会自动处理这些参数。

### 第五章 · 连接服务器（15:00–18:00）★易错点

**操作步骤**：

1. 顶栏 **UMBRA → 服务器**
2. 点 **添加**
3. 填写表单

| 字段 | 值 | 说明 |
|---|---|---|
| 名称 | `kali-lab` | 任意，方便识别 |
| 协议 | `http` | 生产用 https |
| 主机 | `127.0.0.1` | 本机就是服务端 |
| 端口 | `9000` | 服务端默认端口 |
| 密钥 | 粘贴**整行** | `用户名:密码:密钥` |

4. 点 **「认证」** ← 关键！

**旁白**（重点强调）：

> 这里有个**必须注意的点**：填完表单要点「认证」，不能直接关闭。
>
> 为什么？因为**服务器配置只有在认证成功后才写入配置文件**。
>
> 如果你只是填了表单然后关掉，服务器根本没保存。后面创建监听器时，服务器下拉框会是空的，看起来像"点不动"。
>
> 这个设计确实容易让人困惑，我后来加了空状态提示——下拉框空的时候会显示「暂无服务器 - 请先在 UMBRA > 服务器 中添加」。

**验证认证成功**：

```bash
cat ~/.config/umbra/config.json
```

```json
{
  "servers": [
    {
      "id": "...",
      "name": "kali-lab",
      "ip": "http://127.0.0.1",
      "port": "9000",
      "user": "admin",
      "pass": "...",
      "secret": "...",
      "token": "eyJhbGciOiJIUzI1NiIs..."
    }
  ]
}
```

**旁白**：

> 认证成功后，`config.json` 里就有服务器条目了，带一个 JWT token。
>
> 这个 token 有效期默认 7 天。之后每次请求都带上它，服务端验证签名和过期时间。
>
> 好处是**无状态** —— 服务端不存会话，重启也不影响。

**排错指南**：
| 现象 | 原因 | 解决 |
|---|---|---|
| 认证失败 | 密钥格式错 | 检查是否三段、是否完整 |
| 认证失败 | 服务端没启动 | `ss -ltn \| grep 9000` |
| 认证失败 | 端口被防火墙拦 | 检查防火墙规则 |
| 下拉框空 | 没点认证 | 重新添加并点认证 |

### 第六章 · 创建监听器（18:00–20:00）

**操作**：

1. `Shift+L` 打开监听器面板
2. 点 **添加**
3. 填写

| 字段 | 值 | 说明 |
|---|---|---|
| 名称 | `http-8080` | 任意 |
| 类型 | `Channel` | 通道类型 |
| 通道 | `http` | 通信协议 |
| 服务器 | `kali-lab - http://127.0.0.1:9000` | 下拉选择 |
| Port to Open | `8080` | **实际监听端口** |

4. 点 **创建**

**验证**：
```bash
ss -ltn | grep 8080
# LISTEN 0 2048 0.0.0.0:8080 0.0.0.0:*
```

**旁白**：

> 监听器是什么？**它是植入体的"接听电话"端。**
>
> 植入体回连时，连的就是监听器的地址和端口。监听器负责：
> - 接收植入体的心跳
> - 下发操作员的指令
> - 回传执行结果
>
> 为什么不直接让服务端监听，要多一层？
>
> 因为**一个服务端可以挂多个监听器**。你可以同时开 HTTP、HTTPS、SMB、TCP 多个通道，针对不同网络环境用不同通道。这是 C2 框架的灵活性所在。

**知识点卡片**：
| 通道类型 | 适用场景 | 端口 |
|---|---|---|
| HTTP/HTTPS | 最常用，混在正常流量 | 80/443/自定义 |
| SMB | 内网横向 | 445 |
| TCP | 直连，快但不隐蔽 | 自定义 |
| Custom | 自定义协议，对抗检测 | 自定义 |

### 第七章 · 生成植入体（20:00–25:00）★核心

**操作**：

1. `Shift+I` 打开植入体面板
2. 选 **Stageless**（无阶段模式）

**旁白**：

> 先解释两种模式：
>
> **Stageless（无阶段）** —— 所有功能打包成一个文件，一次执行完。简单可靠，但文件大、特征明显。
>
> **Loader（加载器）** —— 分两阶段。第一阶段是小体积"下载器"，运行时再下载完整载荷。隐蔽，但需要额外分发通道。
>
> 新手建议先用 Stageless，稳定。

#### ① 常规（General）

| 字段 | 值 | 原理 |
|---|---|---|
| 编译服务器 | `127.0.0.1:9000` | 由哪台服务端编译 |
| 操作系统 | `Windows` | 目标系统 |
| 架构 | `x64` | 目标 CPU |
| 格式 | `exe` | 可执行文件 |

#### ② C2 通信（★最关键）

| 字段 | 值 | 原理 |
|---|---|---|
| 通道 | `http` | 和监听器一致 |
| **Server 地址** | **`192.168.1.38:8080`** | **宿主机 IP！不是 Kali** |
| 延迟 | `5` 秒 | 心跳间隔 |
| 抖动 | `20`% | 随机化，避免规律性 |

**旁白**（语速放慢）：

> **这里最容易出错！** Server 地址必须填**宿主机的 IP `192.168.1.38`**，端口 `8080`。
>
> 为什么？因为植入体在目标机上运行，它要连的是"能从目标机路由到"的地址。
>
> Kali 的 `10.0.2.15` 目标机根本访问不到，只有宿主机的 `192.168.1.38` 才行。
>
> **延迟和抖动是干什么的？**
>
> 这是**规避流量检测**的关键。
>
> 如果植入体每 5 秒精确回连一次，流量分析一眼就能看出异常——人类不会这么规律。
>
> 加上 20% 抖动，间隔变成 4–6 秒随机，看起来更像正常用户行为。
>
> 这就是 C2 框架的"隐蔽性"设计。

#### ③ 运行时规避（Runtime）

| 选项 | 作用 | 原理 |
|---|---|---|
| AMSI patch | 绕过 PowerShell 恶意脚本检测 | 修改 AMSI 内存 |
| ETW patch | 绕过 Windows 事件追踪 | 修改 ETW 回调 |
| 睡眠掩码 | 休眠时加密内存 | 对抗内存扫描 |
| 字符串混淆 | 隐藏敏感字符串 | 运行时解密 |

**旁白**（重点讲睡眠掩码）：

> 重点讲**睡眠掩码**，这是对抗 EDR 的核心技术。
>
> 植入体休眠时，内存里的恶意代码是明文，容易被杀软扫描到。
>
> 睡眠掩码会在休眠前加密内存，醒来再解密。扫描器扫的时候看到的是乱码。
>
> 常见的实现有 Ekko、Zilean，都是利用 Windows 定时器回调在休眠期间加密内存。

**操作**：点 **Build**，下载生成的 exe

### 第九章 · root 权限下的 9 类操作（27:00–34:00）★核心价值

**画面**：切到 `04-post-exploitation.svg`

#### 9.1 命令执行（`Alt+T`）

```bash
whoami          # root
id              # uid=0(root) gid=0(root)
cat /etc/shadow # 只有 root 能读
```

**旁白**：

> 最基础的能力。root 意味着可以读任何文件、执行任何命令。
>
> `/etc/shadow` 存所有用户的密码哈希，普通用户读不了，root 可以。拿到这个文件就可以离线爆破密码。

#### 9.2 文件操作（`Alt+F`）

**操作**：浏览 `/root/.ssh/`、`/etc/`、`/var/www/`

**旁白**：

> 文件浏览器可以遍历整个文件系统。
>
> 重点看几个位置：
> - `/root/.ssh/id_rsa` —— SSH 私钥，可以直接登录其他机器
> - `/etc/passwd` —— 用户列表
> - `/var/www/html` —— 网站源码，可能有数据库密码
> - `~/.bash_history` —— 历史命令，经常有意外收获

#### 9.3 凭据收集（`Alt+K`）

**旁白**：

> 凭据管理面板集中存储找到的密码、哈希、密钥。
>
> 实战中这一步很重要——收集到的凭据是**横向移动的钥匙**。同一个密码经常在多个系统复用。

#### 9.4 进程查看（`Alt+R`）

**旁白**：

> 看目标上跑了什么。重点找：
> - 杀毒软件、EDR 进程
> - 数据库、Web 服务
> - 其他用户的进程
>
> root 能看到所有进程，包括其他用户的。

#### 9.5 屏幕截图

**操作**：工具栏相机图标

**旁白**：

> 直接看到目标桌面。适合确认目标在做什么、有没有人在操作。

#### 9.6 键盘记录

**旁白**：

> 记录目标用户的键盘输入。可以抓到密码、聊天内容。
>
> **注意**：这个功能涉及隐私，只能在明确授权的测试中使用。

#### 9.7 横向移动 —— SOCKS 代理（`Shift+N`）★重点

**操作**：
1. 打开网络面板
2. 添加 → 类型选 `socks`
3. 监听端口 `1080`
4. 目标主机 `192.168.1.46`

**旁白**（重点讲解）：

> 这是**内网渗透的核心技术**。
>
> 现在我们有了一台内网机器的 root，但目标内网还有其他机器我们访问不到。怎么办？
>
> **把目标机变成代理跳板。**
>
> 配置好 SOCKS 代理后，本地浏览器设置代理 `socks5://192.168.1.38:1080`，所有流量都会经过目标机转发。这样我们就能访问目标所在内网的所有服务了。
>
> 这就是"以点破面"——攻破一台，拿下整个内网。

#### 9.8 权限维持

**旁白**：

> 拿到权限后要考虑：重启后还在不在？
>
> 常见手法：
> - 写 crontab 定时任务
> - 创建 systemd 服务
> - 修改 `.bashrc` / `.profile`
> - 添加 SSH 公钥
>
> 实战中要选择最不容易被发现的方式。

#### 9.9 报告导出（`Shift+R`）

**操作**：打开报告面板 → 创建 → 选 PDF

**旁白**：

> 测试做完要交报告。UMBRA 会自动记录：
> - 执行过的所有命令
> - 发现的所有 IOC（失陷指标）
> - 失陷主机清单
>
> 支持 PDF、HTML、JSON 三种格式。
>
> 这是**专业渗透测试和瞎搞的区别**——有完整的证据链。
