## 镜头 2 · 项目定位（0:45–2:00）

**画面**：切到架构图 `01-architecture.svg`

**旁白**：

> 先说清楚 UMBRA 是什么。
>
> 它是一个**后渗透测试框架**，也叫 C2 框架。
>
> 关键在"后"这个字。它**不负责打进去**——不挖漏洞、不发钓鱼、不做初始访问。它负责的是：**你已经进去了，接下来怎么办**。
>
> 具体来说：
> - 稳定保持访问权限
> - 在目标上执行命令
> - 收集凭据和文件
> - 以这台机器为跳板进内网
> - 最后产出一份可交付的报告
>
> 如果只有裸 shell，这些事都要手工做，效率极低，而且容易丢访问。C2 框架就是把这些重复工作工程化。

**画面**：三层架构图逐层高亮

**旁白**：

> UMBRA 采用**三层架构**：
>
> **操作员客户端** —— Electron + React 写的桌面程序，就是我们看到的界面
> **团队服务器** —— Python + FastAPI，默认监听 9000，是中枢
> **植入体** —— 运行在目标机器上，主动回连服务端
>
> **最关键的设计：客户端和植入体永不直接通信。**
>
> 这一点决定了后面所有操作方式，我会反复提到。

## 镜头 6 · 工程细节（8:00–11:00）★加分项

**画面**：安装日志滚动，逐条高亮

**旁白**：

> 安装过程中我讲几个**工程细节**。这部分能看出一个项目和玩具的区别。

### 细节一 · t64 包名迁移

**画面**：日志里 `libgtk-3-0t64`

> Ubuntu 24.04 之后，很多系统库因为 64 位时间戳迁移改了名字。比如 `libgtk-3-0` 变成了 `libgtk-3-0t64`。
>
> 如果脚本硬编码旧名字，在新系统上直接报错退出。
>
> UMBRA 的做法：**维护一张新旧对照表，自动检测**。新名字不行就用旧名字。
>
> 这样同一份脚本能同时兼容 Ubuntu 22.04、24.04、Kali、Debian。

### 细节二 · tmpfs 空间陷阱

**画面**：`df -h /tmp` 显示 1.9G

> 这个坑我实际踩到了。
>
> 很多系统上 `/tmp` 是**内存盘**，Kali 这里只有 1.9G。而打包 AppImage 需要 2G 以上，会报 `ENOSPC: no space left on device`。
>
> 诡异的是 `df -h /` 显示还有 25G 可用 —— 因为 `/tmp` 是独立的 tmpfs。
>
> UMBRA 的处理：**把 `TMPDIR` 重定向到磁盘目录**。
>
> ```bash
export TMPDIR="${main_dir}/.build-tmp"
```
>
> 一行解决。

### 细节三 · 逐包安装

**画面**：日志里逐个 `apt install`

> 不是一次性 `apt install 一堆包`，而是**逐个装**。
>
> 为什么？因为如果列表里有一个包名不可用，`apt` 会整体失败，整个安装中断。
>
> 逐个装的话，某个包不可用只警告，其他继续。**只有真正关键的基础包失败才退出**。

### 细节四 · libfuse2 缺失

**画面**：日志里 `[warn] libfuse2 absent`

> Kali 只提供 libfuse3，没有 libfuse2。而 AppImage 格式需要 libfuse2 才能挂载运行。
>
> UMBRA 的处理：**运行时检测**，没有 libfuse2 就自动加 `--appimage-extract-and-run`，先解压再运行。
>
> 用户不用管，无感。

**旁白（总结这段）**：

> 这四个细节说明什么？
>
> **一个成熟项目要考虑真实环境的复杂性。** 不是"在我机器上能跑"就完事，而是要考虑：用户可能用 Ubuntu 22、24、Kali、Debian；`/tmp` 可能是内存盘；某个包可能改名了。
>
> 这些处理不写也能跑，但用户会遇到各种奇怪错误。写好了，用户体验就是"一条命令搞定"。

# 第三幕 · 启动与连接（12:00–20:00）

## 镜头 8 · 创建操作员密钥（12:00–14:00）

**画面**：终端

```bash
cd /opt/umbra
./umbra.py server key add admin
```

**输出**（重点展示，高亮三段）：
```
admin:CjzeeStPQ9wfCnyH5iwHKzK:BtdxBz5pYq4fcOpF...
Operator created successfully: admin
Saved: /opt/umbra/admin.key
```

**旁白**：

> 这是**三段式密钥**：`用户名:密码:密钥`。
>
> 为什么设计成三段？这是**双因素认证**：
>
> | 段 | 验证什么 | 存储方式 |
> |---|---|---|
> | 用户名 | 标识身份 | 明文 |
> | 密码 | 你知道什么 | bcrypt 哈希 |
> | 密钥 | 你持有什么 | 明文，128 字符 |
>
> 关键点：**服务端存的是密码的 bcrypt 哈希，不是明文**。即使数据库被拖走，攻击者也拿不到明文密码。
>
> 而密钥是明文存的，所以它必须足够长 —— UMBRA 生成的是 128 字符。
>
> **整行都要保存**，只显示这一次。

**画面**：`cat /opt/umbra/admin.key`

**旁白**：

> 文件在 `admin.key`，随时可以查看。

## 镜头 11 · 连接服务器（17:30–20:00）★易错点

**画面**：客户端 → UMBRA → 服务器 → 添加

**旁白**：

> 现在连接服务器。顶栏 UMBRA → 服务器 → 添加。

**画面**：填表单，逐字段讲解

| 字段 | 值 | 说明 |
|---|---|---|
| 名称 | `kali-local` | 任意，方便识别 |
| 协议 | `http` | 本机测试用 http |
| 主机 | `127.0.0.1` | 服务端就在本机 |
| 端口 | `9000` | 服务端默认端口 |
| 密钥 | 粘贴整行 | `admin:xxx:yyy` |

**旁白**：

> 密钥粘贴整行，客户端会自动解析成三段。

**画面**：鼠标移到「认证」按钮，高亮

**旁白**（语速放慢，重点）：

> **这里有个必须注意的点：填完表单要点「认证」，不能直接关闭。**
>
> 为什么？因为**服务器配置只有在认证成功后才写入 `config.json`**。
>
> ```
> 填表单 → 点认证 → 服务端验证 → 返回 JWT → 写入 config.json
>                 ↓
>             失败则不保存
> ```
>
> 如果你只填表单然后关掉，服务器根本没保存。后面建监听器时，服务器下拉框会是空的，看起来像"点不动"。
>
> 这是新手最容易卡住的地方。我后来加了个空状态提示 —— 下拉框空的时候会显示「暂无服务器 - 请先在 UMBRA > 服务器 中添加」。

**画面**：点认证，状态灯变绿，提示 Authenticated

**旁白**：

> 认证成功，状态灯变绿。

**画面**：终端验证

```bash
cat ~/.config/umbra/config.json
```

**输出**：
```json
{
  "servers": [
    {
      "name": "kali-local",
      "ip": "http://127.0.0.1",
      "port": "9000",
      "user": "admin",
      "token": "eyJhbGciOiJIUzI1NiIs..."
    }
  ]
}
```

**旁白**：

> 配置文件里有内容了，带一个 JWT token。
>
> 这个 token 有效期默认 7 天。之后每次请求都带上它，服务端验证签名和过期时间。
>
> 好处是**无状态** —— 服务端不存会话，重启也不影响已认证的客户端。

**画面**：排错表字幕

| 现象 | 原因 | 解决 |
|---|---|---|
| `Invalid credentials` | 密钥某段错 | 检查三段完整性 |
| `Expired session` | JWT 失效 | 重新认证 |
| 连接超时 | 服务端没起 | `ss -ltn \| grep 9000` |
| **下拉框空** | **没点认证** | **重新添加并点认证** |

# 第四幕 · 监听器与植入体（20:00–28:00）

## 镜头 12 · 创建监听器（20:00–22:00）

**画面**：`Shift+L` → 添加

**旁白**：

> 按 `Shift+L` 打开监听器面板，点添加。

| 字段 | 值 | 说明 |
|---|---|---|
| 名称 | `http-8080` | 任意 |
| 类型 | `Channel` | 通道类型 |
| 通道 | `http` | 通信协议 |
| 服务器 | `kali-local` | 下拉选择 |
| Port to Open | `8080` | **实际监听端口** |

**画面**：点创建，然后终端验证

```bash
ss -ltn | grep 8080
# LISTEN 0 2048 0.0.0.0:8080 0.0.0.0:*
```

**旁白**：

> 创建成功，8080 在监听了。

**旁白（讲原理）**：

> 监听器是什么？**它是植入体的"接听电话"端。**
>
> 植入体回连时，连的就是监听器的地址和端口。监听器负责：
> - 接收植入体心跳
> - 下发操作员指令
> - 回传执行结果
>
> **为什么不直接让服务端监听，要多一层？**
>
> 因为**一个服务端可以挂多个监听器**：
>
> ```
> 服务端 :9000
> ├── 监听器 A :8080  (HTTP)   → 能出网的 Windows 目标
> ├── 监听器 B :8443  (HTTPS)  → 有流量检测的环境
> ├── 监听器 C :445   (SMB)    → 纯内网横向
> └── 监听器 D :1080  (TCP)    → 直连场景
> ```
>
> 不同网络环境用不同通道。这是 C2 框架灵活性的核心。

**画面**：通道类型对比表

| 通道 | 端口 | 适用场景 | 隐蔽性 |
|---|---|---|---|
| HTTP | 80/8080 | 通用，首选 | 高 |
| HTTPS | 443/8443 | 有流量检测 | 最高 |
| SMB | 445 | 内网横向 | 中 |
| TCP | 自定义 | 直连低延迟 | 低 |

## 镜头 13 · 网络陷阱（22:00–25:00）★全片最重要

**画面**：切到网络拓扑图 `02-network-topology.svg`

**旁白**：

> 现在讲**全片最重要的部分**。90% 的人卡在这里。

**画面**：终端查 IP

```bash
ip addr show eth0 | grep inet
# inet 10.0.2.15/24
```

**旁白**：

> 我的 Kali 在 NAT 网络里，IP 是 `10.0.2.15`。
>
> 这是 VirtualBox 内部的私有地址，**外部世界根本路由不到**。
>
> 意味着：
> - Kali **能主动访问**目标 ✅
> - 目标**无法反向连回** Kali ❌
>
> 而植入体是**主动回连**的。如果 C2 地址填 Kali 的 IP，回连 100% 失败。
>
> **这就是为什么很多人照着教程做，会话永远不上线。**

**画面**：在目标机验证

```bash
ping 10.0.2.15
# 100% packet loss
```

**旁白**：

> 实测确认，目标机 ping 不通 Kali。

**画面**：切到宿主机 PowerShell

```powershell
VBoxManage controlvm kali natpf1 "umbra-http,tcp,,8080,,8080"
```

**旁白**：

> 解决方案：**端口转发**。
>
> 这条命令的意思是：宿主机的 8080 → 转发到 Kali 的 8080。
>
> 所以植入体的 C2 地址要填**宿主机的 IP**，不是 Kali 的 IP。

**画面**：验证转发

```powershell
VBoxManage showvminfo kali --machinereadable | findstr Forwarding
# Forwarding(0)="umbra-http,tcp,,8080,,8080"
```

**画面**：三种场景对比表

| 场景 | C2 地址填什么 |
|---|---|
| 目标和 Kali 同网段 | Kali 的 IP |
| Kali 在 NAT 后 | **宿主机 IP** + 配端口转发 |
| Kali 有公网 IP | 公网 IP，建议 443 + https |

**旁白（总结）**：

> 判断标准只有一条：**从目标机能不能访问到这个地址？**
>
> 验证方法：在目标机执行 `curl http://<地址>:8080`。能连上就对了。

## 镜头 14 · 生成植入体（25:00–28:00）

**画面**：`Shift+I` → 选 Stageless

**旁白**：

> 按 `Shift+I` 打开植入体面板，选 Stageless（无阶段模式）。
>
> 两种模式的区别：
> - **Stageless** —— 所有功能打包成一个文件，一次执行完。简单可靠，但文件大。
> - **Loader** —— 分两阶段，第一阶段是小体积下载器。隐蔽，但需要额外分发通道。
>
> 新手先用 Stageless。

**画面**：填常规配置

| 字段 | 值 |
|---|---|
| 编译服务器 | `127.0.0.1:9000` |
| 操作系统 | 目标系统 |
| 架构 | `x64` |
| 格式 | `exe` / `elf` |

**画面**：填 C2 配置，鼠标停在 Server 地址

**旁白**（重点）：

> **这里最容易出错！** Server 地址必须填**目标机能访问到的地址**。
>
> NAT 场景下填宿主机的 IP，端口 8080。
>
> **延迟和抖动是干什么的？**
>
> 这是**规避流量检测**的关键。
>
> 如果植入体每 5 秒精确回连一次，流量分析一眼就能看出异常 —— 人类不会这么规律。
>
> 加上 20% 抖动，间隔变成 4–6 秒随机，看起来更像正常用户行为。
>
> ```
> 实际间隔 = delay × (1 ± jitter/100)
> ```

**画面**：运行时规避选项

| 选项 | 作用 |
|---|---|
| AMSI patch | 绕过 PowerShell 恶意脚本检测 |
| ETW patch | 绕过 Windows 事件追踪 |
| 睡眠掩码 | 休眠时加密内存，对抗内存扫描 |
| 字符串混淆 | 隐藏敏感字符串 |

**旁白（重点讲睡眠掩码）**：

> 重点讲**睡眠掩码**，这是对抗 EDR 的核心技术。
>
> 植入体休眠时，内存里的恶意代码是明文，容易被杀软扫描到。
>
> 睡眠掩码会在休眠前加密内存，醒来再解密。扫描器扫的时候看到的是乱码。
>
> 常见实现（Ekko、Zilean）利用 Windows 定时器回调在休眠期间完成加解密。

**画面**：点 Build，下载 exe

## 镜头 16 · 后渗透实战（30:00–36:00）★核心价值

**画面**：切到后渗透能力图 `04-post-exploitation.svg`

**旁白**：

> 现在讲**拿到 root 之后能做什么**。这是 C2 框架的核心价值。

### 操作 1 · 命令执行（`Alt+T`）

```bash
whoami          # root
id              # uid=0(root)
cat /etc/shadow # 只有 root 能读
```

**旁白**：

> 最基础的能力。root 意味着可以读任何文件、执行任何命令。
>
> `/etc/shadow` 存所有用户的密码哈希，普通用户读不了，root 可以。拿到这个文件就可以离线爆破密码。

### 操作 2 · 文件浏览（`Alt+F`）

**画面**：浏览 `/root/.ssh/`

**旁白**：

> 文件浏览器可以遍历整个文件系统。重点看几个位置：
>
> | 路径 | 找什么 |
> |---|---|
> | `/root/.ssh/id_rsa` | SSH 私钥，可直接登录其他机器 |
> | `/etc/passwd` | 用户列表 |
> | `/var/www/html` | 网站源码，可能有数据库密码 |
> | `~/.bash_history` | 历史命令，经常有意外收获 |

### 操作 3 · 凭据收集（`Alt+K`）

**旁白**：

> 凭据管理面板集中存储找到的密码、哈希、密钥。
>
> 实战中这一步很重要 —— 收集到的凭据是**横向移动的钥匙**。同一个密码经常在多个系统复用。

### 操作 4 · 进程查看（`Alt+R`）

**旁白**：

> 看目标上跑了什么。重点识别：
>
> | 进程特征 | 可能是 |
> |---|---|
> | `clamd` | ClamAV |
> | `falcon` | CrowdStrike |
> | `osqueryd` | Osquery |
> | `auditd` | Linux 审计 |
> | `mysqld` | 数据库 |
>
> root 能看到所有进程，包括其他用户的。

### 操作 5 · 屏幕截图

**画面**：点相机图标

**旁白**：

> 直接看到目标桌面。适合确认目标在做什么、有没有人在操作。

### 操作 6 · 键盘记录

**旁白**：

> 记录目标用户的键盘输入。可以抓到密码、聊天内容。
>
> **注意**：这个功能涉及隐私，只能在明确授权的测试中使用。

### 操作 7 · 横向移动 SOCKS 代理（`Shift+N`）★重点

**画面**：网络面板 → 添加 → socks → 端口 1080

**旁白**：

> 这是**内网渗透的核心技术**。
>
> 现在我们有了一台内网机器的 root，但目标内网还有其他机器我们访问不到。怎么办？
>
> **把目标机变成代理跳板。**
>
> 配置好 SOCKS 代理后，本地浏览器设置代理 `socks5://127.0.0.1:1080`，所有流量都会经过目标机转发。这样我们就能访问目标所在内网的所有服务了。
>
> ```
> 你的机器 → 目标机:1080 → 内网其他机器
> ```
>
> 这就是"以点破面" —— 攻破一台，拿下整个内网。

### 操作 8 · 权限维持

**旁白**：

> 拿到权限后要考虑：重启后还在不在？
>
> 常见手法：
>
> | 方法 | 隐蔽性 |
> |---|---|
> | crontab 定时任务 | 中 |
> | systemd 服务 | 中 |
> | .bashrc / .profile | 低 |
> | 追加 SSH 公钥 | 中 |
>
> 实战中选最不容易被发现的。测试完成后记得清理。

### 操作 9 · 报告导出（`Shift+R`）

**画面**：报告面板 → 创建 → PDF

**旁白**：

> 测试做完要交报告。UMBRA 会自动记录：
> - 执行过的所有命令
> - 发现的所有 IOC
> - 失陷主机清单
>
> 支持 PDF、HTML、JSON 三种格式。
>
> 这是**专业渗透测试和瞎搞的区别** —— 有完整证据链，可交付、可复现、可审计。

## 镜头 18 · 三层如何配合（39:00–39:30）★呼应主线

**画面**：三层架构图，数据流高亮

**旁白**：

> 最后回到开头那条主线：**三层架构如何配合**。
>
> ```
> 操作员在客户端点"执行命令"
>         ↓
> 客户端通过 HTTP API 发给服务端
>         ↓
> 服务端把指令放进队列，等植入体下次心跳
>         ↓
> 植入体回连时取走指令，执行
>         ↓
> 结果原路返回：植入体 → 服务端 → 客户端
>         ↓
> 操作员看到输出
> ```
>
> **每一层各司其职**：
> - 客户端负责**交互**
> - 服务端负责**协调和存储**
> - 植入体负责**执行**
>
> 这个设计的好处：客户端可以随时关，植入体依然在线；植入体被分析，也拿不到操作员信息。
>
> **理解了这条链路，你就理解了所有 C2 框架的本质。**
